# L11 Multi-Agent 多智能体协作（对标书 Ch10）

> 🟩 书主线课。是 L4 编排/路由的自然延伸,也接住你刚做的 reflection(actor-critic)。
> 百度 JD1/3 点名"多智能体协作/Agent 社会"。

---

## §0 最小记忆集（三个锚点）

1. **两个正交维度定架构**:① 上下文**共享 vs 隔离**(= 线程 vs 进程) ② 协作**拓扑**(对等/管理者/去中心化)。
2. **何时值得上多 Agent——唯一硬判据:协作是否引入了单 Agent 生成时"拿不到的新信息"?**
   引入了(执行反馈/视觉/工具验证)→ 显著有效;没引入(自我审查/纯辩论)→ 通常无效甚至有害。
3. **多 Agent 很贵**(Anthropic 披露约 15× token),收益必须大到能盖住数倍成本,否则**调好的单 Agent 更划算**。

---

## §1 维度一:上下文是否共享(最基础的架构决策)

**类比钉死:共享上下文 = 线程,不共享 = 进程。**

| | 共享上下文（线程） | 不共享上下文（进程） |
|---|---|---|
| 后一个 Agent 看到什么 | 前一个的**完整轨迹**(对话+思考) | 只看到**显式传过来**的信息 |
| 协调方式 | 隐式(继承上下文) | 显式(文件/消息/结构化接口) |
| 隔离性 | 无(一处写坏全崩) | 强(可安全并行) |
| 上下文膨胀 | 快(累积) | 每个 Agent 只装自己那份 |
| 成本 | 单轨迹接力,随阶段累积 | 多 Agent 各自展开,**总 token 常高数倍~一个量级** |

**选择依据(书表10-1)**:子任务少(2-3)/窗口装得下/串行/无需隔离 → **共享**;子任务多需并行/单窗口装不下/要信息隔离(如安全审查不该看原始思考) → **不共享**。
**经验法则**:预期累计上下文 > 窗口 50% → 不共享;信息零损耗是硬约束 → 共享;多数真实系统 = **阶段切换式**(前几个共享,到信息饱和点切成不共享 + 显式 handoff)。

**不共享时怎么通信?**(IPC 两范式,操作系统的老答案)
- **共享内存** = 共享文件系统(快,但并发冲突留给你);
- **消息传递** = ① 工具调用参数(同步、结构化) ② 消息总线 Message Bus(异步中转,适合并行协调)。
- Go 名言:"不要通过共享内存来通信,而要通过通信来共享内存"——数据归属清晰 vs 快但易冲突,这个取舍全章反复出现。

## §2 维度二:协作拓扑（不共享上下文时才有得设计）

> 共享上下文时拓扑通常**退化成一条角色切换序列**(没多少架构决策)。真正要设计拓扑的是不共享上下文。按复杂度递增:

- **对等协作 Peer**（2-3 个平等 Agent 迭代改进）:起草↔批注,反复几轮。**你的 reflection 就是这个的雏形**(actor↔critic)。
- **管理者 Orchestration**（中心 Manager 规划+调度,子 Agent 各管一摊）:项目经理带专业工程师。**最常用的生产形态**。
- **去中心化 Decentralized**（无运行时中心,Agent 互相沟通/对等移交 handoff / group chat）:A2A 协议跨组织。

> 术语:2026 流行的 "Graph Engineering"(节点=Agent/程序/人,边=依赖/条件路由/失败去向)就是拓扑的工程化说法;书仍用更稳的"协作拓扑/编排"。你 L9 的 LangGraph 正是画这种图。

## §3 ⭐ 何时真正优于单 Agent（本章最重要判据,面试必问）

**唯一核心判据:协作过程是否引入了单个 Agent 在生成时无法获得的新信息?**

书表10-2:
| 协作模式 | 引入新信息? | 效果 |
|---|---|---|
| 同一模型自我审查(重读自己输出) | **否** | **通常无效甚至有害** |
| 不同 Agent 辩论同一段文本 | 否 | 与单 Agent 持平(等算力) |
| Reviewer 用**测试执行结果**审代码 | **是**(执行反馈) | 显著提升 |
| Reviewer 用**渲染截图**审前端 | 是(视觉) | 显著提升 |
| Reviewer 用**外部工具**验证事实 | 是(工具) | 显著提升 |

- RLEF(2025):用代码执行反馈迭代 >> 独立多次采样。WebGen-Agent:视觉反馈把 26.4%→51.9%。
- **解释了"学术说单 Agent 够、工程说多 Agent 好"的矛盾**:学术比的是"看同一段文本互相讨论"(无新信息);工程有效的多 Agent 都带**外部反馈环**(执行/视觉/工具)。
- **⚠️ 直接打你脸的呼应**:你上节做的 reflect = **同一模型自我审查**(表10-2 第一行"通常无效甚至有害")!这正是为什么你 6 场景实测**全 accept**——它没引入新信息。要让它真有效,得给它 actor 拿不到的**新信息**(如真调工具验证草稿声称的金额、或换更强模型/外部规则)。你"该不该每轮反思"的直觉,书用这条判据给了理论支撑。

**成本**:Anthropic 多 Agent 研究系统 token ≈ 普通对话 **15×**,且 token 用量本身解释约 80% 的性能差异 → 收益必须盖得住数倍开销。
**步骤预算**:单纯给更多步数≠更好(Agent 缺"预算意识"会浅层饱和);Manager 应按子任务复杂度**动态分配预算**。

## §4 失败模式（多 Agent 独有的坑,面试加分）

1. **共享文件系统的并发冲突**:多 Agent 同时读写同一产物 → 覆盖/竞态(共享内存范式的老问题)。缓解:锁/消息传递/单写者。
2. **错误的级联放大**:上游 Agent 一个错误判断,被下游当权威继续放大 → 整条链跑偏。缓解:每个 handoff 点做校验/质量门控、限制信任传递。

## §5 Agent 社会（前沿谈资,不深挖）

斯坦福 AI 小镇(生成式 Agent 社会模拟)、狼人杀(信息不对称策略博弈)、Vending-Bench/Agent 经济。校招"能讲一层"即加分,不必实现。

## §6 接到你的项目

- 你的客服 capstone 该上多 Agent 吗?**用 §3 判据自检**:把它拆成"路由 + 订单/退款/政策专家"能引入新信息吗?——不能(都是同一模型看同样数据),纯属把一个 loop 拆成几个、加成本。**结论:当前不值得**(和你 reflection 门控的判断同源)。
- 真要用多 Agent,得是引入外部反馈的场景(如"生成→真跑测试→按结果改")。

---

## §7 一句话总结

> 多 Agent 不是"多几个 loop 更聪明",而是**两个架构维度(上下文共享/隔离 × 拓扑)的工程选型**;
> 是否值得,只看一条:**协作有没有引入单 Agent 拿不到的新信息**——没有就别上,一个调好的单 Agent + 15% 的钱更香。
