# 阶段二 Capstone · 电商售后智能客服 Agent —— 设计稿

> 由一次**模拟面试**驱动产出(2026-07-27)。教练扮演面试官(面创科技 leader),
> 用户主导设计,逐块被压力追问。本文是「设计面」两轮通过后的收敛蓝图,**明天进第三轮:动手搭 + code review**。
> 用途:阶段二 capstone / 简历项目。综合 L1–L8 全部能力。

## 场景与一期范围
- 平台每天几十万条售后咨询,人工成本扛不住,Agent 先扛一部分。
- **一期做**:订单/物流查询、退款申请、退换货政策答疑。
- **一期不做**:使用教学、商品导购。

## 需求拆解:澄清一个模糊需求的 7 个维度(面试满分答法)
澄清沿三条线索:**边界(做什么/不做什么)· 真值(答案从哪来/准不准)· 风险(谁授权/怎么兜底/怎么衡量)**。

| # | 维度 | 结论 |
|---|---|---|
| 1 | 范围边界 | 见上(查询/退款/政策答疑) |
| 2 | 高危操作+权限 | 退款金额 **≤¥200 且状态明确合规** → Agent 直接执行;超阈值/有疑义 → 只生成工单转人工 |
| 3 | 知识来源+真实性 | 有《退换货政策》(MD+PDF,~40页),**覆盖不全**(跨境/定制/活动 → 转人工),**会不定期更新** |
| 4 | 成功指标/验收 | 质量:**自动化率(deflection)** + **事实准确率/幻觉率**(需人工抽检 / LLM-judge,不能模型自评);业务:token 成本 vs 人工成本 + **转人工率**;安全:**分级**的事故率(且难点在**检测**——不投诉就不知道悄悄退错款 → 要审计日志) |
| 5 | 身份与数据 | **易漏项**:必须确认「来问的人=订单本人」,否则越权泄露(把张三订单答给李四)。→ 工具层归属校验 |
| 6 | 会话形态+规模 | 几十万条/天 → 不能每条用最贵模型、上下文不能无限涨。多为个位数轮对话 |
| 7 | 转人工/降级 | 明确 escalation 触发条件 + Agent 挂了/超时的兜底 |

## 收敛后的架构蓝图

**① 整体形态 —— 分层:意图路由(模型)+ 高危执行(代码)**
> ⚠️ 面试栽点纠正:路由权 ≠ 全交代码。**「意图路由用模型(灵活),高危执行用代码(可靠)」是两层,各管一层。**
- 意图路由:**LLM-as-router + 结构化输出**(L4 + L6 缺口2),输出受约束 `intent` 枚举
  `{query_order, query_logistics, ask_policy, request_refund, other}`,`temperature=0`,便宜小模型。
- 只有 `ask_policy` 分支走 RAG(省钱);查订单/退款不碰向量库。
- 单 loop,**不带 planner**(客服延迟敏感 + 短对话,规划纯添延迟;对应锚点 Q3)。

**② 工具层**
- `query_order` / `query_logistics`:**工具层强制 `where user_id = session.user.id`**;
  `user_id` **由代码从已登录会话注入,绝不接受模型输出的 id**(防越权)。
- `search_policy`:RAG 检索(仅 ask_policy 分支)。
- `process_refund`:**高危**。模型可决定「调」,但**代码在执行前拦阈值**(≤¥200 且状态合规才放行)。
- `escalate_to_human`:显式转人工工具(可审计、能终止 loop)。

**③ 知识层(政策答疑)**
- RAG:chunking + embedding + 向量库(L7)。**chunk 切小切准**(chunking 决定 RAG 上限)。
- **覆盖不全 → 挡幻觉转人工**:检索**相似度低于阈值即转人工**;阈值**从 L7 评估集标定**
  (太严→过度转人工,太松→幻觉泄漏,precision/recall 权衡);可加 grounding 校验(LLM 判「答没答上」)。
- **会更新**:更新较慢 → 每次政策更新后**重跑 embedding 刷新向量库**。
- ❌ 弃用最初的「关键词命中直接甩政策」层(L4/L7 已证脆弱:「我不想退款,只是问问…」会误伤)。

**④ 记忆/上下文**
- 开局**预加载** session 客户信息(customer_id、active 订单)进 context,省查询往返。
- **上下文杀手不是对话轮数,是 RAG 检索载荷**(top-k×chunk = 每轮上千 token)→ 控法是**检索更准 + 压 top-k**,
  **不 summarize 政策原文**(会丢「7天无理由」这种精确措辞);会话历史可 summarize。
- 冲突处理:客户提供与 context 冲突的信息 → 转人工(求稳)或加 verify 工具核验后覆盖。
- **限对话轮数**(如 8 轮未解决 → 转人工),省 token + 省用户时间。

**⑤ 安全/兜底**
- 退款阈值、转人工条件、审计:**hard-code 在代码,不让 LLM 判**(可靠性来自约束,不来自模型话术;L5/L8)。
- 高危操作前二次确认 + 结构化审计日志(为「检测」事故,#4)。

## 明天第三轮:动手搭(带着盖楼)
- 先定文件蓝图 → 纵切打通最小可跑链路(如「查订单」一条)→ 逐层加厚(退款阈值/RAG/转人工)。
- 门禁三条:环境可复现 / 至少 1 正 1 反 pytest 绿 / 无调试残留。
- 复用资产:L7 的 `eval/` 评估集(改 RAG/prompt 必跑回归)、L5 记忆存取、L6 上下文预算、L8 executor 三类分流。
- **由教练切第一刀**(定第一个文件 + 第一条最小链路),用户从空文件带着写。

## 未来增强(设计已想清,留待可选实现 / LangChain 版对比)
- **RAG 三档置信度路由(confidence-band)**:当前是二档(距离≤1.15 覆盖答 / >1.15 转人工)。
  升级为三档——`<t_lo` 直接答 / `t_lo~t_hi`(标定出的"沟" 1.09~1.34)**反问澄清让用户 rephrase→重检索** / `>t_hi` 转人工。
  中间档用"改进 query 再检索"挽回边界问题,压幻觉同时降转人工率(1 轮澄清 << 1 次人工)。
  变体"总结 top-1 反问'您是想问退款政策吗'"要防**假前提诱导 + 隐私**(政策无主、风险低)。
  → LangGraph 版可用 conditional edge 优雅实现,作裸 SDK vs 框架的对比素材。
- **阈值是运营旋钮**:1.15 由 `calibrate_threshold.py`(eval 13 条分布)标定,上线后按真实误判率回调,`eval/` 回归网兜底。
